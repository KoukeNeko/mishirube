# 資料庫開啟與啟動失敗修正計畫

日期：2026-10-17。狀態：實作與本機驗證完成；待實機更新驗收。

## 目標與依據

目標：資料庫暫時不可讀、遭鎖定、版本不相容或真正損毀時，App 保留原資料並清楚呈現失敗；條件恢復後可以重試，不再將一次開啟失敗轉成空白資料庫。

本次已驗證的事實：

- 實機的舊資料庫被改名為 `.corrupt-*`，之後啟用另一份資料庫；舊檔仍能通過 SQLite 完整性與 App 讀取檢查。
- 使用現有 `AppDatabase.open` 已重現：健康的 WAL 資料庫遭鎖定，回傳 `SQLITE_BUSY (5)`，也會被隔離並建立新庫。
- 原始實機例外未被記錄，因此不能確定當時的第一個錯誤碼，也不能將 iOS 檔案保護或記憶體壓力視為已確認原因。
- 資料合併與實機回寫已完成；程式修正必須以保留目前資料為前提。

範圍維持在 SQLite 連線、啟動錯誤介面、iOS 資料可用性、必要診斷與回歸測試。延續目前 SQLite、服務層、AppStore 與既有 UI 元件的架構。

## 一、修正後的行為契約

| 狀況 | 預定行為 |
| --- | --- |
| 第一次安裝，主檔與既有資料痕跡皆不存在 | 建立資料庫、完成 migration，再執行既有首次初始化 |
| 既有正常資料庫 | 開啟原檔，依既有 migration 升級 |
| `BUSY` | 先使用有上限的 SQLite 等待；仍失敗則關閉此次連線，顯示可重試狀態 |
| `LOCKED` | 保留原檔，回報鎖定；不假設 `busy_timeout` 能處理這種錯誤，也不任意重跑交易 |
| iOS 受保護資料尚不可用 | 等待可用性通知；可用後啟動一次重試 |
| 無法開啟、權限、I/O 或儲存空間錯誤 | 保留原檔，顯示存取失敗；只有原生可用性確實為 false，才判定為等待解鎖 |
| `CORRUPT` 或 `NOTADB` | 保留原檔及相關交易檔，顯示需要檢查／復原；不自動建立替代空庫 |
| 資料庫版本高於 App | 拒絕開啟並提示版本不相容，不執行 migration |
| migration 失敗 | 回滾交易、關閉連線，保留原資料並回報 migration 階段與原始錯誤 |
| 主檔缺失但仍有 WAL、SHM 或舊版 `.corrupt-*` | 視為既有資料異常，不當成第一次安裝 |
| 背景連線找不到主檔 | 拒絕連線，不建立資料庫 |

既有的零長度檔案或缺少必要資料表的檔案，也不能只因 SQLite 可以開啟，就當成全新安裝灌入範例資料。新建與既有檔案必須在初始化入口明確區分。

任何失敗流程都不得改名、刪除、截短或替換原庫，不得改用記憶體範例庫，也不得藉由重新初始化掩蓋錯誤。SQLite 本身必要的 WAL 復原與快取維護，與應用程式自行搬移／重建檔案分開看待。

## 二、依序實作

### 1. 取消自動隔離重建，修正連線生命週期

主要檔案：`lib/backend/storage/database.dart`、`lib/backend/storage/schema.dart`、`lib/backend/backend.dart`。

- 移除 `AppDatabase.open` 捕捉所有 `SqliteException` 後呼叫 `_setAside`、重開新庫的行為。
- 保留主錯誤碼、延伸錯誤碼、原始例外及 stack trace；失敗階段至少區分開啟、連線設定、schema 檢查與 migration。不以錯誤訊息字串判斷類型。
- 將目前的 `busy_timeout=5000` 移到 WAL 設定及第一次 schema 存取之前。先沿用既有五秒上限，不再疊加多輪五秒重試；等待結束後交由啟動介面處理。
- 既有檔案使用不會建立檔案的開啟模式。只有主啟動入口確認為新安裝時，才允許建立檔案。
- `AppDatabase.connect` 僅連接已存在、版本符合的資料庫；由主連線負責新建、migration 與 WAL 模式設定，背景連線不切換模式或自行升級。
- 明確交接連線所有權：設定、驗證或 migration 失敗時，已建立的連線關閉一次；成功後才交給 `AppDatabase`。`StateError` 等非 SQLite 失敗也適用。
- 保留 migration 的交易與回滾語意，使用既有 schema 定義作為唯一來源。

完成條件：真實鎖定測試不再產生 `.corrupt-*` 或替代空庫；解除鎖定後，原本的同一筆資料仍能讀到。背景連線遇到缺檔時不會留下新檔。

### 2. 讓啟動失敗可見、可重試

主要檔案：`lib/main.dart`、`lib/app/app.dart`，以及一個職責單純的啟動狀態元件，例如 `lib/app/startup.dart`。

- 將啟動區分為讀取中、等待資料可用、可重試失敗、版本／資料格式錯誤及成功。
- 失敗時顯示使用者可理解的狀態與「重試」，不只停在啟動畫面或丟出未處理例外。等待解鎖時由通知觸發重試。
- 一次只執行一個初始化。重試按鈕、回到前景、解鎖通知不得各自建立一份 Backend 或 AppStore。
- `MishirubeApp` 目前在 `store == null` 時會建立記憶體範例資料。正式啟動成功前不得進入這條預覽／測試路徑，也不得進入 onboarding。
- 資料庫及必要初始化全部成功後，才建立正式 AppStore、掛載正常 App，並啟動健康同步、提醒、WatchSync 與 HomeWidgets。
- 初始化中途失敗時，關閉此次已建立的 Backend；重試成功後，相關監聽與副作用只註冊一次。
- 沿用主題、語系設定與共用頁面／按鈕元件；錯誤頁不能依賴尚未建立的 AppStore。
- 優先沿用既有字串；必要的新字串補齊繁中、簡中、英文、日文、韓文。

建議畫面狀態用語為「等待解鎖」「資料無法讀取」「資料格式無法辨識」「版本不相容」，依可確定的原因呈現，避免將所有錯誤都稱為損毀。

完成條件：資料庫開啟失敗時，畫面可操作；沒有空白範例資料、onboarding、健康寫入或 Widget 快照覆寫。成功重試後才顯示原資料。

### 3. 接入 iOS 資料可用性，涵蓋背景寫入

主要檔案：`ios/Runner/AppDelegate.swift`、啟動狀態元件、`lib/backend/application/health_service.dart`、`lib/backend/application/health_writer.dart`，必要時小幅銜接 `lib/app/app_store.dart`。

- 沿用專案 MethodChannel 註冊方式，提供 `UIApplication.isProtectedDataAvailable` 查詢，以及受保護資料可用性變更通知。
- 在 SQLite 開啟前檢查；不可用時等待通知，不定時輪詢、不持續嘗試開檔。
- 涵蓋首次啟動及健康資料背景連線。等待中的健康同步接回現有單一同步工作，資料不可用時不啟動新一輪讀寫。
- 可用性查詢與實際開檔之間仍可能再次鎖定，因此真正的開啟例外仍走步驟 1 的保留原庫路徑，不能把預檢當成保證。
- 背景連線失敗傳回呼叫端，保留可重試狀態與診斷；不以開新庫或忽略錯誤處理。
- 平台條件集中在一個小型存取入口；Android 與桌面不呼叫 iOS 通道。
- 保持現有檔案保護強度。這項修正不需要改變 bundle ID、簽章、權限或 entitlement。

完成條件：測試可控制「不可用 → 可用」轉換，確認只在可用後開庫一次；與回到前景事件同時發生時，也只有一個初始化／同步工作。

### 4. 保存最小診斷，移除誤導的舊恢復狀態

主要檔案：資料庫開啟／啟動程式、`lib/app/app_store.dart`、`lib/features/me/me_screen.dart`、`lib/l10n/`。

- 在 App 私有支援目錄保存單一、有界限的本機啟動診斷檔，與 SQLite 分開；保留最近一次失敗及其後成功解決的時間。
- 內容限於時間、App／schema 版本、平台、失敗階段、錯誤分類、SQLite 主／延伸碼及新建／既有檔案狀態。
- 不保存 SQL 參數、餐點或健康資料、憑證、token、完整絕對路徑；不自動上傳。
- 診斷檔寫入失敗不能蓋掉原始開庫錯誤，也不能觸發任何重建；記錄本身失敗作為次要錯誤回報。
- 不再以只存於記憶體的 `recoveredFrom` 宣稱已恢復。同步清理失去用途的 `recoveredDatabasePath`、舊警告及對應語系字串。
- 舊版遺留 `.corrupt-*` 保留原狀；不自動選擇、搬回、合併或刪除。

完成條件：失敗後重新啟動仍能取得原始分類與錯誤碼；成功後可分辨事件已解決。診斷資料不進入使用者資料封存或稽核內容。

### 5. 回歸測試、建置與實機更新

先將既有「文字檔無法讀取便建立新庫」測試改為新契約：回報錯誤且保留原檔。這是刻意修正錯誤行為，不是放寬測試。

| 測試 | 必須證明 |
| --- | --- |
| 健康資料庫遭真實獨占鎖定 | 等待有上限；沒有改名、替換空庫；解鎖後原資料仍在 |
| 等待期間鎖定解除 | 本次開啟可成功，沒有落入錯誤恢復路徑；由另一 isolate／程序釋放鎖，避免同 isolate 的 Timer 被同步 SQLite 阻塞 |
| 已提交、未 checkpoint 的 WAL，程序突然結束 | 重開後已提交資料存在，交易不被丟棄，不建立空庫 |
| `NOTADB`／真正無法讀取的檔案 | 可辨識失敗、原始內容保留、沒有新範例資料 |
| 新版 schema／migration 失敗 | 不降級、不重建；交易回滾，失敗連線關閉後可重新處理 |
| 背景 `connect` 遇到缺檔或版本不符 | 不建立新檔、不執行 migration |
| 首次安裝與缺檔殘留交易檔 | 乾淨新安裝可正常初始化；有既有資料痕跡時停止並呈現錯誤 |
| iOS 不可用 → 可用；前景事件同時發生 | 不可用時無 SQLite 操作；可用後單次初始化／同步 |
| 啟動失敗 → 重試成功 | 失敗期間沒有預覽庫、onboarding、健康／Widget 副作用；成功後顯示原資料 |
| 診斷保存及隱私 | 跨啟動仍保留分類；沒有憑證或使用者內容；記錄失敗不遮蓋原始錯誤 |
| 五語系、放大文字、平台差異 | 錯誤狀態可呈現並可重試，Android 不依賴 iOS 通道 |

檔案雜湊只用於適合的案例，例如已知文字檔及被鎖定、未取得存取的資料庫；不把「所有情況 DB／WAL／SHM 雜湊都不變」當成通用斷言。SQLite 合法 checkpoint 或 SHM 快取維護可能改變實體檔案，主要驗收是原資料、已提交交易及檔案身分未被替換。

驗證順序：

1. 確認 Flutter 3.47.x；格式化變更檔，執行資料庫、啟動與通道的針對性測試。
2. `flutter analyze` 無問題、完整 `flutter test` 通過，再完成受影響的 iOS 建置。
3. 在 Mac 使用實機資料的副本驗證升級與封存往返；逐表比對資料、刪除標記、關聯及同步游標。個人資料不加入 Git 或測試 fixtures，公開測試全部使用合成資料。
4. 實作與檢查完成後，依使用者指示更新實機。更新前重新備份當下資料，保留目前既有資料容器並正常升級安裝，不以卸載重裝驗收。
5. 驗證一般啟動、強制結束後重開、鎖定後回前景及使用者安排的重開機／首次解鎖。驗收前後記錄資料識別碼、數量、tombstone、audit 與完整性結果，排除正常同步新增造成的差異。

## 三、交付順序與完成條件

第一個實作切片完成步驟 1、2 及對應回歸測試，先封住會產生空庫的路徑；第二個切片完成步驟 3、4，再做步驟 5 的整合與實機驗收。

完成條件：

- 已知 `BUSY` 重現案例不會使原資料從 App 消失。
- 已提交 WAL 可在程序突然終止後恢復。
- 開啟、migration、背景連線、資料不可用及版本錯誤均不會建立替代空庫。
- 使用者能辨識啟動失敗並安全重試；一次成功只建立一份正常 App 與同步工作。
- 實機原有資料與目前復原內容均保留，診斷足以辨識下一次真正的失敗原因。
- 相關測試、靜態檢查及受影響建置通過，工作區既有其他修改不被覆蓋。

本計畫不要求資料庫 schema 變更。若實作時發現具體相容性需求，先說明原因並補上必要的 migration／封存驗證，不重寫已發布 migration。

## 四、實作與本機驗證結果

- 已移除自動隔離重建與舊恢復警告。既有檔案不使用建立模式；背景連線不建立、升級或切換 journal 模式。開啟失敗保留原始例外、錯誤碼、階段與 stack trace，並關閉此次連線。
- 已加入獨立啟動介面、單次初始化與重試；正式 AppStore 成功前不掛載正常 App。iOS 原生可用性查詢與通知集中於 `StorageAccess`，健康同步沿用既有單一工作，受保護資料不可用時不開始同步或推進游標。
- 診斷使用獨立 JSON，保留最近失敗與解決時間；內容僅包含允許的欄位。診斷／關閉失敗沿用 Flutter 錯誤回報機制，只回報去除內容的次要錯誤，不遮蓋原始開庫錯誤。
- 已補上真實 BUSY、另一 isolate 解鎖、程序強制結束後 WAL 恢復、缺檔與殘留檔、背景 isolate 失敗傳遞、migration 回滾、診斷隱私、啟動重試、通知競態、健康同步中途鎖定與多語系放大文字測試。
- Flutter 3.47.5／Dart 3.13.4：完整 `flutter test` 1,963 項通過；`flutter analyze --no-pub` 無問題；`flutter build ios --debug --no-codesign --no-pub` 成功。
- 已在 Mac 使用合併資料庫的獨立副本驗證：35 個資料表逐表指紋不變，涵蓋資料、刪除標記與設定／同步游標；35 表封存匯出、還原、再匯出的資料及 extensions 一致，完整性檢查為 `ok`，外鍵錯誤為 0。原合併資料庫的 SHA-256 不變。
- Schema 維持版本 6，已發布 migration SQL 未變動。既有範圍外修改保留，沒有建立 commit。

尚未將修正版安裝至 iPhone。本機 iOS 建置未簽章；實機保留先前回寫的合併資料。後續依使用者指示，先備份當下資料，再正常升級安裝，驗收一般啟動、強制結束、鎖定／解鎖及重開機後首次解鎖。
